### 1. Vault Build Pipeline (ibc_vault)

**Refactored `scripts/vault-compiler.cjs` (complete rewrite)**
- Old: Per-domain vault zips (one per scraper domain)
- New: 4 single unified global vaults — `laws`, `cases`, `documents` (stub), `forms` (stub)
- `laws` vault: aggregates statutory markdown from all domain subdirs under `output/temp_md/`
- `cases` vault: reads directly from `summaries/super_summary/` (17,418 files, ~64 MB raw)
- Stubs skip gracefully when source folder doesn't exist
- `--vault laws|cases|all` flag for targeted rebuilds
- Writes `output/client_vaults/dist/latest.json` with SHA-256 checksums after build

**Created `scripts/publish-vaults.sh`**
- Monthly release wrapper: compile → GitHub Release (via `gh` CLI) → patch `latest.json` URLs
- Reads `GH_REPO` from env; auto-computes ISO week tag (e.g. `vault-2025-W30`)
- Generates release notes from zip sizes automatically

### 2. Activation API Server (`HAYAGRIVA/api-server/`)

New Express.js server to be deployed at `api.hayagriva.app` on Railway.

**Files created:**
- `index.js` — 3 endpoints: `POST /activate`, `GET /vaults/latest.json`, `GET /health`
- `db.js` — SQLite license store (`findLicense`, `touchActivated`, `insertLicense`, `revokeLicense`)
- `scripts/seed-license.js` — adds/upserts license keys; test keys `HAYG-TEST-0000-000{1,2}`
- `railway.toml` — Railway deployment config with health check on `/health`
- `.env.example` — template with `VAULT_KEY_LAWS`, `VAULT_KEY_CASES`, etc.
- `data/latest.json` — placeholder manifest served by `/vaults/latest.json`
- `README.md` — DNS setup (Namecheap CNAME for `api` subdomain), endpoint docs, Railway deploy steps

**License key format:** `HAYG-XXXX-XXXX-XXXX`
**Activation flow:** User enters key → app POSTs to `/activate` → server returns `vaultKey` → stored in macOS/Windows Keychain under `hayagriva / vault-{type}`

**Note:** `npm install` with native compile (`better-sqlite3`) fails on Node 24 + macOS locally due to C++20 Clang issue. Railway (Linux Node 20) builds fine. Local dev: use `--ignore-scripts`.

### 4. Architecture Decisions (Brainstorm / Research)

**Sovereign LLM Strategy — finalized:**
- **REMOVE cloud option** from Settings (OpenRouter/Gemini/OpenAI path to be hidden, not deleted yet)
- **REMOVE Ollama** from local path entirely
- **Replace with llamafile** — distributable via `www.hayagriva.app`, same license/download flow as vaults
- Two modes only: `lite` (search-only) and `local` (llamafile inference)

**Model analysis (BharatGen):**
- `LegalParam-2.9B` — Q4_K_M GGUF ~1.7 GB, 2,048 token context, ✅ runs on 16GB Mac
- `FinanceParam-2.9B` — same specs, Indian financial law domain
- `Param2-17B MoE` — 2.4B active params, 4,096 token context, ~10 GB GGUF — ❌ won't fit comfortably on 16GB Mac (needs 24GB+)

**Fine-tuning roadmap (v2 model):**
- Fine-tune `Param-1-2.9B-Instruct` (LegalParam base) on IBC dataset
- Dataset: synthesize Q&A pairs from 17,418 case summaries using Gemini API (85K+ training pairs)
- Training: QLoRA on RunPod A100 (~$50–100 per run, 6–12 hrs)
- Distribution: GGUF Q4_K_M → llamafile → Cloudflare R2 → hayagriva.app

**v1 plan (ship now):** Use BharatGen's existing LegalParam/FinanceParam — just GGUF quantize and wrap as llamafile. Infrastructure same.
